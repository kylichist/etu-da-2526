## Блок A. Теоретические вопросы

### A1. Зачем формальная верификация, если есть тесты?

Тест прогоняет **одно** чередование (interleaving) шагов `worker(0)` и
`worker(1)`. У параллельной программы таких чередований огромное число.
Model checking (SPIN) перебирает **все** достижимые состояния и доказывает
свойство для каждого. Тест может «случайно» не поймать гонку, верификация —
нет.

### A2. Почему Promela — язык моделирования, а не программирования?

Promela-программа **не исполняется на процессоре**, она описывает конечную
формальную модель (структуру Крипке). Отсюда ограничения: все переменные с
**конечным** диапазоном (иначе бесконечное пространство состояний), нет
функций — только процессы (`proctype`), параллелизм — основа языка.

### A3. Что такое структура Крипке для нашей модели?

Состояние = `(A, B, C, done, содержимое канала, счётчики команд init/
worker(0)/worker(1))`. Переходы = каждый исполнимый оператор. Симуляция
идёт по **одному** пути этого графа, верификация обходит **весь** граф.
Размер вектора состояния в нашем прогоне — 292 байта.

### A4. LTL: операторы и два класса свойств.

- `[]` (G, always) — во **всех** состояниях; `<>` (F, eventually) —
  **когда-нибудь**; `U` — until; `->`, `!`, `&&`, `||`.
- **Safety** «ничего плохого никогда» — `[] φ`, нарушается **конечным**
  контрпримером.
- **Liveness** «хорошее когда-нибудь» — `<> φ`, нарушается **бесконечным**
  контрпримером (зависание).

### A5. Почему нужны ОБА свойства, а не одно?

- Только `liveness` `<> done` — докажет, что программа завершится, но
  **ничего** не скажет о правильности `C`.
- Только `safety` `[] (done -> C верна)` — формально **истинна даже если
  программа никогда не завершается** (тогда `done` всегда `false`, и
  `false -> …` тривиально истинно).
- Вместе = «завершится **И** результат правильный».

### A6. Что такое never claim?

SPIN проверяет не саму формулу, а её **отрицание**: строит автомат Бюхи
(never claim), принимающий ровно те вычисления, которые формулу
**нарушают**. Если конечное состояние claim `"-end-"` **недостижимо** —
нарушения нет (`errors: 0`). Поэтому строка `1 of N states unreached` в
`claim` — это **доказательство корректности**, а не предупреждение.

### A7. Семантика канала.

`chan row_computed = [N*N] of {byte,byte,int}` — FIFO-очередь на 9
сообщений-кортежей. Буфер **полон** → отправитель `!` блокируется; буфер
**пуст** → получатель `?` блокируется. Особый случай `[0]` — рандеву
(синхронный канал, отправка и приём одновременно).

### A8. Почему в `C` нет гонки (race condition)?

Архитектурно: **единственный писатель** в `C` — `worker(0)`. `worker(1)`
в `C` не пишет вообще, он только шлёт в канал (`main.pml:47-48`). У коллег
(`friends-main.pml`) в `C` пишут оба воркера — там гонки нет лишь потому,
что строки не пересекаются, а синхронизация идёт через счётчик `finished`
и `atomic`.

## Блок B. Вопросы по коду `main.pml`

### B1. Как строки делятся между процессами?

`worker(id)` берёт `row = id` и идёт с шагом `P` (`main.pml:21,54`):
строки `id, id+P, id+2P, …`. При N=3, P=2: `worker(0)` → строки 0 и 2;
`worker(1)` → строка 1. Распределение задаётся **арифметикой, без
синхронизации**.

### B2. Почему тип сообщения `{byte,byte,int}`?

`{номер_строки, номер_столбца, значение}`. Индексы 0…N−1 влезают в `byte`;
значение — `int`, т.к. `test.py` подаёт элементы −10…10 и произведения/
суммы могут быть большими/отрицательными.

### B3. Почему `C` объявлен `int`, а не `byte`?

Та же причина: отрицательные и большие значения в тестах. У коллег `byte`
работает только потому, что их данные `[1..8]`, максимум `C` = 50.

### B4. Почему `done = true` — последнее действие worker(0)?

`done` — не часть алгоритма, это **датчик для верификатора**. Он ставится
**после** сборки из канала и печати (`main.pml:110`), поэтому `done==true`
гарантированно означает «`C` полностью собрана и корректна» — на этом
держатся обе LTL-формулы.

### B5. Как worker(0) знает, сколько читать из канала?

`expected_elements` (`main.pml:62-73`): для каждой строки `i` с
`i % P != 0` (то есть не «своей») добавляет `N`. При N=3,P=2 только `i=1`
даёт `+3`, итого 3. Затем ровно 3 раза делает блокирующий
`row_computed?r,c,val` (`main.pml:79-86`).

### B6. Почему `:: row >= N -> break`, а не `else`?

`do…od` недетерминированно выбирает любую ветку с истинным охранным
условием. `<` и `>=` взаимоисключающие — недетерминизма нет, это
**условие выхода**. Если бы ни одна ветка не была истинна — процесс
заблокировался бы.

### B7. Зачем `atomic` вокруг запуска воркеров (`main.pml:131-138`)?

Чтобы оба воркера стартовали «разом», до начала работы любого из них:
детерминированный старт и меньше лишних состояний. (У коллег `atomic`
нужен ещё и для защиты счётчика `finished` от гонки.)

## Блок C. Практические задания (изменить код) + ожидаемый вывод

> Перед каждым прогоном: `spin -a main.pml && gcc -w -o pan pan.c`,
> затем `./pan -a -N liveness` и `./pan -a -N safety`.

### C1. «Сломайте свойство безопасности — что покажет SPIN?»

Изменить в `main.pml:145` одно число: `C[0] == 43` → `C[0] == 44`.
**Ожидание:** `./pan -a -N safety` → `errors: 1` (или больше), создаётся
файл `main.pml.trail`, depth контрпримера конечный (safety нарушается
**конечным** путём — это и есть определение safety). `liveness` при этом
остаётся `errors: 0`. Восстановить 43.

### C2. «Уберите `[]` из safety».

`ltl safety { (done -> (...)) }` (без `[]`). **Ожидание:** `errors: 0`, но
проверка фактически **не выполнена**: формула без темпорального оператора
оценивается лишь в начальном состоянии, где `done==false`, значит
`false -> …` ≡ `true` (`1 state, depth 0`, воркер даже не запускается).
Именно этот баг чинили в git-коммите *fix: safety feature* — показывает,
что понимаешь зачем `[]`.

### C3. «Сделайте канал синхронным (рандеву): `[N*N]` → `[0]`».

`chan row_computed = [0] of {byte,byte,int}`. **Ожидание:** всё ещё
`errors: 0` для обоих свойств. Дедлока нет: `worker(0)` не зависит от
канала, пока считает свои строки, и гарантированно доходит до
`row_computed?`; `worker(1)` на каждом `!` ждёт приёма (рандеву).
Меняется только пространство состояний, не корректность. Хороший ответ:
«буфер влияет на размер модели, а не на результат — здесь один писатель и
строгий порядок».

### C4. «Поменяйте N=4, P=3 (или N=4, P=2)».

Изменить `main.pml:2,4`. Нужно **пересчитать эталон `C = A×B`** вручную
(данные `A`,`B` придётся дописать для N=4, `main.pml:117-123`) и обновить
9→16 равенств в `ltl safety`. Суть ответа: формула safety **жёстко
привязана к конкретным A,B** — её надо переписывать при смене данных,
liveness — нет.

### C5. «Внесите гонку: пусть worker(1) тоже пишет в `C` напрямую».

`main.pml:47-48`: заменить `row_computed!row,col,sum;` на
`C[row*N+col] = sum;`. **Ожидание:** канал остаётся пустым, но
`expected_elements` всё равно = 3, и `worker(0)` навсегда блокируется на
`row_computed?` → `done` никогда не станет `true` → **`liveness`
нарушается** (`./pan -a -N liveness` → `errors: 1`, контрпример —
бесконечный/тупиковый путь). Вывод: канал здесь несёт **синхронизацию**,
а не только данные.

### C6. «Поставьте P=1».

`#define P 1`. **Ожидание:** один воркер = `worker(0)`, все строки «свои»,
`expected_elements = 0`, канал не используется вовсе, оба свойства
`errors: 0`. Показывает, что канал задействуется только при `P > 1` и
неравномерной нагрузке.

## Блок D. Каверзные вопросы «на засыпку»

### D1. «`make run` проверяет safety?»

**НЕТ.** В модели два never claim; `./pan` без `-N` берёт **первый по
умолчанию — `liveness`** (SPIN прямо пишет `defaults to -N liveness`).
`safety` надо запускать **вручную**: `./pan -a -N safety`. Это самый
частый «лови на слове».

### D2. «`spin -T` — это “не выводить трассу”?»

Нет. `-T` = **не делать отступы в выводе `printf`** (`spin --help`:
`-T do not indent printf output`). Без него матрица печатается с большими
отступами.

### D3. «Симуляция доказала корректность?»

Нет. Симуляция (`spin -T main.pml`) — **один случайный путь**. Она
показывает, что модель *в принципе работает*. Доказывает свойство только
верификация (`./pan`), перебирающая **все** пути.

### D4. «`1 of 6 states unreached in claim` — это ошибка/мёртвый код?»

Нет, **наоборот**. Это недостижимое финальное `"-end-"` состояние
never claim — «нарушение зафиксировано». Его недостижимость = SPIN не
нашёл ни одного пути к нарушению свойства. Согласуется с `errors: 0`.

### D5. «`visited > stored` в прогоне liveness — почему?»

Для liveness используется **вложенный (nested) DFS**: каждое состояние
может посещаться дважды (внешний поиск + поиск цикла), поэтому
`transitions = visited + matched`, а у safety `= stored + matched`.

### D6. «Чем `test.py` отличается от верификации?»

`test.py` — функциональный оракул: гоняет 21 кейс через **симуляцию**
(`spin` без `-a`), сравнивает с Python-эталоном. Это много разных `A,B` на
**одном** пути. `./pan` — один `A,B` на **всех** путях. Дополняют друг
друга, не заменяют.

## Блок E. Построение структуры Крипке у доски

> Могут попросить «постройте структуру Крипке для вашего алгоритма».
> Главное — правильно сказать, **что такое состояние**, честно
> объяснить **почему полный граф не рисуют руками**, и нарисовать
> **абстракцию** канала (производитель–потребитель).

### E0. Что такое состояние нашей модели

Состояние = **значения всех глобальных переменных + счётчики команд
(PC) всех процессов**:
`(A, B, C, done, содержимое_канала, PC_init, PC_worker0, PC_worker1)`.
Переход = один исполнимый оператор одного процесса. Начальное
состояние = старт `init`.

### E1. Почему полный граф не рисуют (и это правильный ответ)

В реальном прогоне — **2301 состояние**, вектор состояния **292 байта**
(27 `int` в трёх массивах + буфер канала + PC трёх процессов). Руками
это невозможно — **и в этом весь смысл model checking**: структуру
Крипке строит и обходит SPIN, а не человек с мелом. У доски строят
**абстракцию**: выкидываем арифметику умножения и сами числа `A,B,C`,
оставляем только то, что отвечает за **синхронизацию** — обмен через
канал между `worker(1)` (производитель) и циклом приёма `worker(0)`
(потребитель).

### E2. Абстракция: производитель–потребитель на канале

При N=3, P=2 по каналу идёт ровно строка 1 = **3 сообщения**.
Абстрагируем:

- `worker(1)` — производитель: делает `sent` отправок (`row_computed!`),
  `sent ∈ 0..3`.
- `worker(0)` — потребитель: посчитал свои строки, затем в цикле делает
  `recv` приёмов (`row_computed?`), `recv ∈ 0..3`; при `recv == 3`
  печатает и ставит `done = true`.
- Буфер канала `[N*N] = 9 ≥ 3` ⇒ производитель **никогда не блокируется**;
  блокироваться может только потребитель — на **пустом** канале
  (`recv == sent`).

Состояние абстракции: `(sent, recv)` с инвариантом `recv ≤ sent ≤ 3`.
Чтобы граф влез на доску, покажем форму на **2 сообщениях** (та же
логика, меньше узлов); терминал `(2,2)` = «принято всё → печать →
`done=true`»:

```
   (0,0) ──send──► (1,0) ──send──► (2,0)
                     │ recv          │ recv
                     ▼               ▼
                   (1,1) ──send──► (2,1)
                                     │ recv
                                     ▼
                                   (2,2)  =  done = true
```

- `send`: `sent++` (производитель), доступен пока `sent < 2` (буфер не
  полон — здесь всегда).
- `recv`: `recv++` (потребитель), доступен **только если** `recv < sent`
  (иначе канал пуст → `worker(0)` блокируется и ждёт `send`).
- Развилки (`(1,0)` идёт и вправо `send`, и вверх `recv`) — это и есть
  **interleaving** шагов двух процессов; SPIN перебирает все пути.

### E3. Что граф доказывает «на глаз»

- **Liveness** `<> done`: из любого узла любой путь рано или поздно
  приходит в `(2,2)` (= `done=true`). Тупиков нет: в `(0,0)` потребитель
  «ждёт», но производитель делает `send` → `(1,0)`; то есть пустой канал
  не вечен.
- **Safety** `[] (done -> C верна)`: `done=true` **только** в `(2,2)`, а
  туда попадаем лишь когда `recv = 2` (все сообщения строки уже разложены
  в `C`). Значит «`done` ⇒ `C` собрана» — ровно смысл формулы.
- **Нет гонки**: в графе нет состояния, где в `C` пишут двое — писатель
  один (`worker(0)`), `worker(1)` только `send` (см. A8).

### E4. Связь абстракции с настоящим прогоном

«Реальная структура Крипке — это произведение трёх таких "осей" (PC
`worker(0)`, PC `worker(1)`, содержимое канала) плюс массивы, отсюда
2301 состояние. Наш граф `(sent,recv)` — её проекция на подсистему
синхронизации. SPIN строит полную структуру неявно и проверяет
`liveness`/`safety` на **всех** её путях; мы у доски показываем ту же
логику на абстракции».
