## Блок A. Теоретические вопросы

### A1. Что такое семафор? `wait`/`signal`.

Целая неотрицательная переменная `S.V` + две **атомарные** операции:
- `wait(S)` (`P`): если `S.V > 0` → `S.V--`; иначе **блокировать** процесс,
  пока не станет `> 0`.
- `signal(S)` (`V`): `S.V++`, разблокирует одного ждущего.

Атомарность критична — иначе сам семафор станет источником гонки.

### A2. Бинарный vs обобщённый (считающий) семафор.

- **Бинарный**: `S.V ∈ {0,1}`, пускает в КС **1** процесс (мьютекс).
- **Обобщённый**: `S.V` любое `≥ 0`, старт `k`, пускает в КС **до `k`**
  процессов. Бинарный — частный случай `k = 1`.

### A3. Зачем симулировать обобщённый бинарными?

(1) Историческая: ряд ОС/платформ давали только бинарные примитивы.
(2) Учебная (главная): классическая нетривиальная задача — много
**ошибочных** алгоритмов было предложено (Бен-Ари специально это
отмечает). Наивное «`wait(S); count--; …`» ломается: процесс с
`count < 0` должен заблокироваться, **отпустив `S`**, иначе встанут все.

### A4. Идея алгоритма Барца. Роли трёх объектов.

- `count` — «значение» симулируемого семафора (сколько слотов осталось),
  старт `k`.
- `S` — бинарный **мьютекс** для атомарности операций над `count`.
- `gate` — бинарный **турникет**: через `wait(gate)` за раз входит лишь
  **один** процесс. На входе: если после `count--` слоты ещё есть
  (`count > 0`) → `signal(gate)` (пускаем следующего); если `count` упал
  до 0 → турникет **не** открываем (следующие застревают на `p1`). На
  выходе: при `count` `0→1` (`count == 1`) → `signal(gate)` — ровно одно
  разрешение одному ждущему.

### A5. Почему алгоритм корректен (своими словами)?

- **Лемма 6.6:** инвариант `count = k − #вКС`.
- **Лемма 6.5(6):** `gate` всегда бинарный (баланс «закрытий» на входе и
  «открытий» на выходе: 1 к 1).
- **Теорема 6.7 (взаимное исключение):** `#вКС ≤ k`. От противного: чтобы
  стало `k+1`, надо войти из `#вКС = k`, но тогда `count = 0` (Лемма 6.6),
  а при `count = 0` турникет закрыт — противоречие.

### A6. Почему busy-wait семафор, а не очередь ждущих?

Для **доказательства взаимного исключения** модель ждущих не важна (Барц
доказывает safety без предположений о справедливости). Busy-wait даёт
наименьшее пространство состояний и точно соответствует §6.10 Бен-Ари.

### A7. Как семафор реализован в Promela (`main.pml:20-21`)?

```promela
#define wait(s)   atomic { s > 0;s-- }
#define signal(s) s++
```
`s > 0` — **голое булево выражение как оператор**: блокируется, пока не
станет истинным (executability) = «ждать, пока семафор свободен». `atomic`
= атомарность. Тонкость: если внутри `atomic` инструкция блокируется,
атомарность **временно снимается** — другой процесс может сделать
`signal`, и `wait` продолжится (поэтому семафор не «дедлочит сам себя»).

### A8. Что доказывает Барц, а что — НЕТ?

Только **взаимное исключение** (`#вКС ≤ k`). **Свободу от голодания НЕ
гарантирует**: при слабых семафорах конкретный процесс может бесконечно
«оттираться» от турникета. Для этого есть алгоритм **Уддинга** (6.14,
следующий параграф книги). Поэтому наш `liveness` намеренно слабый —
«система в целом прогрессирует», а не «каждый войдёт».

## Блок B. Вопросы по коду `main.pml`

### B1. Зачем `critical` (`main.pml:15,45-47`)?

**Не часть алгоритма Барца**, а датчик для верификации: `critical++` на
входе в КС, `critical--` на выходе. `assert(critical <= K)` ловит
нарушение даже в **симуляции**; `ltl mutex` — во всех состояниях при
верификации.

### B2. Почему `gate` объявлен `byte`, а не `bit`/`bool`?

Чтобы **доказать**, что он остаётся бинарным (`ltl bingate {[](gate<=1)}`).
Если объявить `bit`, переполнение скрылось бы (обрезание/ошибка), и баг
алгоритма нельзя было бы наблюдать. `byte` позволяет SPIN **обнаружить**
`gate == 2`, если алгоритм неверен.

### B3. Почему на выходе именно `count == 1`, а не `count > 0`?

`signal(gate)` нужно делать **строго при переходе `count` `0→1`** — ровно
одно «открытие» на каждое «закрытие». `count > 0` приводило бы к
повторным `signal(gate)` → `gate` стал бы `2` (нарушение `bingate` и
далее `mutex`).

### B4. Почему N=4, K=2?

`K=2` ⇒ в КС до 2 процессов. `N=4 > K` ⇒ есть реальное давление на
семафор (4 претендента на 2 слота), проверка взаимного исключения
**нетривиальна**.

### B5. Почему процесс — `do :: true -> … od` без `break`?

Это «loop forever» из листинга 6.13: бесконечный реактивный цикл
«некритическая → вход → КС → выход». Поэтому `-end-` процесса
**недостижим by design** (см. D3).

### B6. Соответствие строк листингу Барца.

Вход: `wait(gate)`=p1, `wait(S)`=p2, `count--`=p3,
`if count>0 -> signal(gate)`=p4/p5, `signal(S)`=p6.
Выход: `wait(S)`=p7, `count++`=p8,
`if count==1 -> signal(gate)`=p9/p10, `signal(S)`=p11.

## Блок C. Практические задания (изменить код) + ожидаемый вывод

> Перед прогоном: `spin -a main.pml && gcc -w -o pan pan.c`, затем
> `./pan -a -N mutex` (и при необходимости `bingate`/`binsem`/`liveness`).
> Проверку дедлока — **без** claim: `spin -a` без `ltl`-фокуса /
> `./pan` на модели без активного claim.

### C1. «Поменяйте местами `wait(gate)` и `wait(S)` на входе».

`main.pml:33-34`: сделать `wait(S); wait(gate);`. **Ожидание:
ДЕДЛОК.** Сценарий: процесс A захватил `S` (S=0) и блокируется на закрытом
`gate`. Процесс в КС хочет выйти, но `p7 wait(S)` ждёт `S`, который держит
заблокированный A → никто не делает `signal(gate)` → система встала.
Прогон **без claim** покажет `invalid end state`, `errors: 1`,
`main.pml.trail`. Классическая иллюстрация «порядок захвата семафоров
важен».

### C2. «Уберите турникет: на входе всегда `signal(gate)`».

`main.pml:36-39`: заменить `if … fi` на просто `signal(gate);`
(то есть убрать охрану `count > 0`). **Ожидание:** турникет всегда
открыт → в КС входит больше `K` процессов → `assert(critical <= K)`
срабатывает уже в **симуляции** (`spin main.pml` → *assertion violated*),
а `./pan -a -N mutex` → `errors: 1` + `.trail`. Возможно также нарушение
`bingate` (gate растёт). Показывает, **зачем** нужен турникет.

### C3. «Замените на выходе `count == 1` на `count > 0`».

`main.pml:52-55`. **Ожидание:** на каждом выходе делается лишний
`signal(gate)` → `gate` может стать `2` → `./pan -a -N bingate` →
`errors: 1` (нарушено `[] (gate<=1)`); вслед за этим обычно ломается и
`mutex`. Показывает критичность условия `0→1`.

### C4. «Поставьте K=3, N=5».

`main.pml:2,5`. **Ожидание:** по-прежнему `errors: 0` для `mutex`
(`[] (critical<=3)`), `bingate`, `binsem`, `liveness`. Алгоритм Барца
корректен для любого `k`. Изменится только размер пространства состояний.
Подчёркивает: формула `mutex` использует `K` (`#define K 3` подставится в
`critical<=3`), переписывать руками 9 равенств, как в части 1, **не
нужно** — свойство параметрическое.

### C5. «Поставьте K=1».

`main.pml:5`. **Ожидание:** `errors: 0`; обобщённый семафор с `k=1` =
**бинарный** = чистое взаимное исключение, `critical <= 1`. Показывает,
что бинарный семафор — частный случай обобщённого.

### C6. «Уберите `atomic` из `wait` (`main.pml:20`)».

`#define wait(s) s > 0;s--`. **Ожидание:** инкремент/декремент перестаёт
быть атомарным, два процесса могут «разорвать» проверку `s>0` и `s--` →
оба пройдут при `s==1` → нарушение `mutex`/`binsem`, `errors: 1` +
`.trail`. Показывает, **зачем** `atomic` в семафоре.

## Блок D. Каверзные вопросы «на засыпку»

### D1. «`assert(critical <= K)` и `ltl mutex` — это дублирование?»

Логически проверяют одно и то же, но: `assert` срабатывает **в точке
кода** и ловится даже в **симуляции** (`spin main.pml`); `ltl mutex` —
глобальное темпоральное свойство, проверяется во **всех** состояниях
через never claim при верификации. Держим оба для надёжности.

### D2. «Почему `invalid end states - (disabled by never claim)`?»

При активном never claim проверка тупиков **отключена**. Поэтому
отсутствие дедлока проверяется **отдельным** прогоном без claim — там
`invalid end states +` и `errors: 0` ⇒ дедлоков нет.

### D3. «`1 of 34 states unreached in proctype process` — мёртвый код?»

**Нет.** Это `-end-` (`main.pml:58`) — неявное конечное состояние после
тела процесса. Наш процесс — бесконечный `do :: true -> … od` без `break`,
управление **никогда** не доходит до `}`. `-end-` недостижим **by
design**, для любого реактивного «loop forever» это норма (на лекции:
можно снять галочку «report unreachable code»). А `unreached in init
(0 of 10)` — наоборот, `init` отработал полностью.

### D4. «`1 of 10 unreached in claim mutex` при `errors: 0`?»

Это финал `"-end-"` never claim (= «нарушение зафиксировано»). Его
**недостижимость** = SPIN перебрал всё пространство и **не нашёл пути к
нарушению** `[] (critical<=2)`. Это **доказательство корректности**, а не
предупреждение.

### D5. «Почему `liveness` слабый — `[]<>(critical>0)`, а не “каждый
процесс войдёт”?»

Потому что Барц **не свободен от голодания** (A8). Сильную
индивидуальную живость доказать нельзя — это принципиальное свойство
алгоритма, а не недочёт модели. `[]<>(critical>0)` означает «система
бесконечно часто прогрессирует» (нет глобального дедлока).

### D6. «`gate=0` — это “занято” или “нет слотов”?»

`gate=0` = турникет **закрыт**: вход перекрыт, потому что либо кто-то
сейчас проходит узкое место `p2…p5` под `S`, либо все `K` слотов заняты
(`count` дошёл до 0 и `signal(gate)` на входе не сделали). Открывается
обратно на выходе при `count` `0→1`.

### D7. «Почему `liveness` запускается с флагом `-f`?»

`-f` = слабая справедливость (weak fairness). Без неё планировщик мог бы
«вечно» игнорировать какой-то процесс и формально получить ложный
контрпример к живости. У safety-свойств (`mutex/bingate/binsem`)
`fairness disabled` — им справедливость не нужна.

## Блок E. Построение структуры Крипке у доски

> Очень вероятное задание: «постройте структуру Крипке для вашего
> алгоритма». Полную строить нельзя (см. E0) — строят **абстрактную**
> для урезанной модели. Ниже — готовый граф, который рисуется за минуту.

### E0. Что такое состояние и почему полный граф не рисуют

Состояние нашей модели = **значения всех глобальных переменных +
счётчики команд (PC) всех процессов**:
`(S, gate, count, critical, PC_init, PC_p1, PC_p2, PC_p3, PC_p4)`.
В реальном прогоне это **1728 состояний**, вектор 60 байт. Руками такое
не рисуют — **в этом и смысл model checking**: SPIN строит структуру
Крипке неявно и обходит её за нас. У доски строят **абстракцию**:
выкидываем `id`, детали входа/выхода, оставляем «фазу» процесса и
ключевые переменные.

### E1. Абстракция: фаза процесса + значение `count`

Сведём каждый процесс к трём фазам (видимый снаружи эффект протоколов
Барца):

| Фаза | Смысл | Что делает с `count` |
|---|---|---|
| `N` | некритическая секция | — |
| `W` | вошёл во вход, ждёт у турникета | — |
| `C` | в критической секции | вход: `count--`; выход: `count++` |

Переход `W → C` возможен **только если** `count > 0` (есть слот) — это и
есть суть Барца после абстрагирования от `S`/`gate`. Состояние
структуры Крипке: `(фаза_P1, фаза_P2, count)`.

### E2. Готовый граф для N=2, K=1 (рисовать этот)

`K=1` (бинарный семафор как частный случай). Старт `count = 1`,
оба в `N`. Шаг = один процесс делает один переход (interleaving).

```
                 ┌───────────────── S0 (N,N,1) ─────────────────┐
            P1:N→W│                                              │P2:N→W
                  ▼                                              ▼
              S1 (W,N,1)                                     S2 (N,W,1)
           P1:W→C│   │P2:N→W                          P1:N→W│   │P2:W→C
        (count1→0)▼   ▼                                      ▼   ▼(count1→0)
           S3 (C,N,0) S5 (W,W,1) ◄───────────────────────────┘   S4 (N,C,0)
        P1:C→N│  │P2  │P1:W→C        P2:W→C│                  P2:C→N│  │P1
       (0→1)  ▼  ▼N→W ▼                    ▼                 (0→1)  ▼  ▼N→W
            S0   S6 (C,W,0)             S7 (W,C,0)              S0   S7
                   │P1:C→N (0→1)           │P2:C→N
                   ▼                       ▼
                 S1 (W,N,1)              S2 (N,W,1)
```

Полный список достижимых состояний (всего **8**):

| | состояние | `#вКС` | `count` |
|---|---|---|---|
| S0 | (N,N,1) | 0 | 1 |
| S1 | (W,N,1) | 0 | 1 |
| S2 | (N,W,1) | 0 | 1 |
| S3 | (C,N,0) | 1 | 0 |
| S4 | (N,C,0) | 1 | 0 |
| S5 | (W,W,1) | 0 | 1 |
| S6 | (C,W,0) | 1 | 0 |
| S7 | (W,C,0) | 1 | 0 |

### E3. Что граф доказывает «на глаз» (главное!)

- **Взаимное исключение.** Состояния `(C,C,·)` в графе **НЕТ** — оно
  недостижимо. Из `S6 (C,W,0)` процесс P2 **не может** сделать `W→C`,
  т.к. `count = 0`. Это `ltl mutex {[](critical<=K)}`: «ни одно
  достижимое состояние не имеет `#вКС > K`».
- **Инвариант Леммы 6.6:** во всех 8 состояниях `count = K − #вКС`
  (`#вКС=0 → count=1`, `#вКС=1 → count=0`). `count` никогда не
  отрицателен и не `2`.
- **Живость** `[]<>(critical>0)`: на любом бесконечном пути по графу
  бесконечно часто встречается состояние с кем-то в `C` (S3/S4/S6/S7) —
  система не застревает.
- **Дедлока нет:** у каждого состояния есть исходящий переход (в S6
  заблокирован P2, но P1 делает `C→N` → S1; симметрично S7).

### E4. Как ответить про реальную K=2, N=4

«В графе появляется состояние `(C,C,·)` с `count = 0` — и это
**нормально**, т.к. `#вКС = 2 = K`. Запрещённым остаётся `#вКС = 3`:
чтобы третий процесс вошёл, ему нужен `W→C` при `count > 0`, но при
двух в КС `count = K − 2 = 0` (Лемма 6.6) — переход заблокирован. То
есть `mutex` = «в структуре Крипке недостижимы все состояния с
`#вКС > K`». SPIN перебирает все 1728 состояний и подтверждает это».
