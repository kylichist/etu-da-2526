## 1. Задание (Вариант 6)

Из `part-2/TASK.md`:

> Реализовать задачу доступа процессов в критическую секцию с помощью
> алгоритма Барца, симулирующего обобщённый семафор с помощью бинарных
> (алг. 6.13 на стр. 126-129 в Бен-Ари).

Расшифровка по словам:

- **Критическая секция (КС)** — участок кода, который не должны одновременно
  выполнять «слишком много» процессов.
- **Обобщённый семафор** — счётчик-разрешитель с начальным значением `k`:
  пускает в КС одновременно **до `k`** процессов.
- **Бинарные семафоры** — семафоры, значение которых только 0 или 1.
- **Алгоритм Барца** — конкретный способ собрать поведение обобщённого
  семафора (с `k > 1`) из двух **бинарных** семафоров плюс целочисленного
  счётчика. Это алгоритм **6.13** из книги M. Ben-Ari, *Principles of
  Concurrent and Distributed Programming* (2-е изд.), §6.10, стр. 126–129.

Итог задания: написать на Promela модель, где `N` процессов соревнуются за
КС, доступ регулируется **не** готовым обобщённым семафором, а его
**симуляцией по Барцу** на двух бинарных семафорах; и формально доказать в
SPIN, что симуляция работает правильно (в КС не более `k` процессов).

В нашей модели: `N = 4` процесса, `k = K = 2` (`main.pml:2,5`).

## 2. Ликбез: что такое семафор

### Проблема, которую решает семафор

Когда несколько процессов работают параллельно и обращаются к общему
ресурсу, шаги процессов **чередуются** (interleaving) произвольным образом.
Классическая беда — *race condition*: операция `x = x + 1` на самом деле это
три шага (прочитать `x`, прибавить 1, записать). Если два процесса выполнят
их вперемешку, одно из приращений потеряется.

Чтобы такого не было, нужен механизм **взаимного исключения**: гарантия, что
в «опасный» участок (критическую секцию) одновременно входит ограниченное
число процессов. Семафор — самый известный такой механизм (Э. Дейкстра,
1965).

### Определение семафора

Семафор `S` — это переменная с целым неотрицательным значением `S.V` и двумя
**атомарными** операциями:

- **`wait(S)`** (он же `P`, «проверить»): если `S.V > 0` — уменьшить `S.V`
  на 1 и пройти дальше; иначе — **заблокировать** процесс, пока `S.V` не
  станет `> 0`.
- **`signal(S)`** (он же `V`, «освободить»): увеличить `S.V` на 1, при этом
  один из заблокированных на этом семафоре процессов может разблокироваться.

Ключевое слово — **атомарно**: `wait`/`signal` неделимы, их нельзя «разорвать»
другим процессом. Без атомарности сам семафор стал бы источником гонки.

### Виды семафоров (важно для нашей реализации)

В литературе различают семафоры по тому, **как именно** ждёт заблокированный
процесс и кого будят:

- **Busy-wait семафор** («активное ожидание»): процесс не засыпает, а в цикле
  проверяет условие `S.V > 0`. Просто описывается формально, поэтому именно
  его используют для **доказательства** корректности алгоритмов. Мы тоже
  моделируем busy-wait семафор (см. §7) — для верификации это и нужно.
- **Слабый (weak) семафор**: разблокирует **произвольный** из ждущих
  процессов. Может приводить к голоданию.
- **Сильный (strong) семафор**: ждущие выстроены в очередь FIFO — голодания
  на самом семафоре нет.

Барц в §6.10 (и мы вслед за ним) рассматривает семафоры как **busy-wait** —
это упрощает рассуждение и достаточно для доказываемого свойства (взаимного
исключения).

## 3. Бинарный vs обобщённый семафор

| | Бинарный семафор | Обобщённый (считающий) семафор |
|---|---|---|
| Значение `S.V` | только **0 или 1** | любое целое `≥ 0` |
| Начальное значение | обычно 1 | любое `k ≥ 0` |
| Смысл | «ресурс свободен / занят» (мьютекс) | «осталось `k` свободных слотов» |
| Сколько в КС | максимум **1** процесс | максимум **`k`** процессов |

Обобщённый семафор с `S.V = k` — естественное обобщение: он пускает в КС не
одного, а до `k` процессов одновременно (например, пул из `k` одинаковых
ресурсов). Бинарный семафор — частный случай `k = 1`.

Главное свойство обобщённого семафора, которое мы хотим воспроизвести и
доказать:

> В критической секции одновременно находится **не более `k`** процессов.

В нашем коде это ровно `ltl mutex { [] (critical <= K) }` (`main.pml:76`).

## 4. Зачем вообще симулировать обобщённый семафор бинарными

Вопрос законный: если нужен обобщённый семафор — почему не взять его готовым?

1. **Историческая/практическая причина.** Ряд ОС и аппаратных платформ
   предоставляли только бинарные примитивы синхронизации (мьютексы,
   lock/unlock). Обобщённый семафор приходилось «собирать» из них.
2. **Учебная причина (главная для нас).** Это классическая нетривиальная
   задача. Очевидные «наивные» решения **некорректны**, и в литературе было
   предложено много ошибочных вариантов (Ben-Ari прямо отмечает: *«it is
   worth studying because so many incorrect algorithms have been proposed for
   this problem»*). Барц (Hans W. Barz, 1983) дал решение, корректность
   которого доказуема.

**Почему «наивно» не получается.** Хочется написать так:

```
binary semaphore S = 1
integer count = k
wait:    wait(S); count--; if count >= 0 then proceed else block; signal(S)
```

— но тут сразу проблема: процесс, у которого `count` ушёл в минус, должен
заблокироваться, **отпустив** `S` (иначе все встанут), а потом, проснувшись,
снова захватить `S`. Аккуратно «разблокировать ровно столько, сколько нужно,
и не потерять и не передвоить разрешения» на двух бинарных семафорах — и есть
суть задачи. Барц решает её через **второй** бинарный семафор `gate`, который
играет роль «турникета» на входе.

## 5. Алгоритм Барца 6.13: идея

Листинг 6.13 из Бен-Ари (стр. 126), один процесс в бесконечном цикле:

```
binary semaphore S    ← 1     // мьютекс для count
binary semaphore gate ← 1     // турникет на входе
integer count         ← k     // целочисл. компонент обобщ. семафора

loop forever
    non-critical section

    // -------- симуляция wait обобщённого семафора --------
p1:  wait(gate)
p2:  wait(S)
p3:  count ← count − 1
p4:  if count > 0 then
p5:      signal(gate)
p6:  signal(S)

    critical section

    // -------- симуляция signal обобщённого семафора -------
p7:  wait(S)
p8:  count ← count + 1
p9:  if count = 1 then
p10:     signal(gate)
p11: signal(S)
```

Три объекта и их роли:

- **`count`** — собственно «значение» симулируемого обобщённого семафора:
  сколько ещё процессов можно впустить. Стартует с `k`.
- **`S`** — обычный бинарный мьютекс. Нужен только чтобы операции над `count`
  (`count--`, проверка, `count++`) были атомарны относительно друг друга.
  Захвачен в `p2…p6` и в `p7…p11`.
- **`gate`** — бинарный «турникет». Это и есть хитрость Барца. Через `p1
  wait(gate)` в protocol входа за раз проходит **только один** процесс.
  Дальше он сам решает, **передать ли турникет следующему**:
  - если после декремента `count > 0` (слоты ещё есть) — он делает `p5
    signal(gate)`, «пропуская» следующего;
  - если `count` упал до 0 (слотов больше нет) — он **не** делает
    `signal(gate)`, и `gate` остаётся 0 → следующие процессы **застревают на
    `p1`**.

Турникет снова открывается на выходе: когда процесс покидает КС и `count`
поднимается с 0 до 1 (`p9: if count = 1`), он делает `p10 signal(gate)` —
именно одно разрешение, ровно для одного ждущего на входе.

Грубая интуиция: `gate` гарантирует, что в «узком месте» `p2…p5`
одновременно крутится максимум один процесс, поэтому `count` не «пробьют»
наперегонки; а сам `count` считает оставшиеся слоты. Барц аккуратно
балансирует: на каждое «закрытие» турникета (когда `count` дошёл до 0) ровно
одно «открытие» на выходе (когда `count` вернулся к 1).

## 6. Почему алгоритм Барца корректен

Бен-Ари доказывает корректность через систему инвариантов. Своими словами и
в привязке к нашим переменным:

Введём `entering` — «процесс находится между `p2` и `p6`» (внутри узкого
места под `S`), и `#inCS` — число процессов в самой КС.

- **Лемма 6.5.** Совместно инвариантны (в числе прочего):
  - `#entering ≤ 1` — под `S` одновременно не более одного процесса (это
    обеспечивает `S` как мьютекс);
  - `entering → gate = 0` — пока кто-то проходит вход, турникет закрыт;
  - `(gate = 0) ∨ (gate = 1)` — **`gate` всегда бинарный** (формула 6.5(6)).
    Это нетривиально: `gate` объявлен как обычная переменная, и то, что он
    не превысит 1, нужно доказывать. Мы это проверяем в SPIN как
    `ltl bingate` (`main.pml:79`).
- **Лемма 6.6.** Инвариант `count = k − #inCS`. То есть `count` — это в
  точности «сколько ещё слотов осталось»: `k` минус число тех, кто уже в КС.
- **Теорема 6.7 (взаимное исключение).** Из лемм следует `#inCS ≤ k`.
  Доказательство от противного: чтобы `#inCS` стало `k+1`, надо войти из
  состояния `#inCS = k`; но тогда по Лемме 6.6 `count = 0`, а войти в КС
  можно только пройдя вход, где при `count` ушедшем в 0 турникет закрыт —
  противоречие.

Именно `#inCS ≤ k` мы и моделируем счётчиком `critical` и проверяем
`ltl mutex { [] (critical <= K) }`. SPIN перебирает **все** чередования
`N` процессов и подтверждает, что нарушить это невозможно.

## 7. Как семафор реализуется в Promela

Promela — язык **моделирования** для SPIN, а не язык программирования. Готового
типа «семафор» в нём нет, но busy-wait семафор выражается элементарно
(Ben-Ari, §6.15):

```promela
// main.pml:20-21
#define wait(s)   atomic { s > 0;s--}
#define signal(s) s++
```

Разбор:

- `atomic { ... }` — блок выполняется **без чередования** с другими
  процессами. Это и есть требуемая **атомарность** операций семафора (§2).
- Внутри `wait`: первый «оператор» — это **выражение** `s > 0`. В Promela
  булево выражение само по себе является инструкцией, которая **блокируется,
  пока не станет истинной** (executability). Это и есть «ждать, пока семафор
  свободен» — причём именно *busy-wait*: процесс не двигается, пока `s > 0`
  ложно. Как только `s > 0` — тут же атомарно `s--`.
- `signal` — просто `s++`. Атомарность одного присваивания в Promela
  гарантирована и без `atomic`.

Тонкость про `atomic` и блокировку: если внутри `atomic` инструкция
блокируется (`s > 0` при `s == 0`), атомарность временно «снимается» —
другой процесс может выполнить `signal` и поднять `s`, после чего наш `wait`
продолжится. Поэтому семафор на `atomic { s > 0; s-- }` работает корректно и
не приводит к дедлоку «сам в себе».

Почему именно busy-wait, а не очередь ждущих: для **доказательства**
взаимного исключения модель ждущих не важна (Барц доказывает safety без
предположений о справедливости), а busy-wait даёт наименьшее пространство
состояний и точно соответствует рассуждению из §6.10 Бен-Ари.

## 8. Разбор `main.pml` строка за строкой

### Константы (`main.pml:2,5`)

```promela
#define N 4   // число конкурирующих процессов
#define K 2   // k — начальное значение обобщённого семафора
```

`K = 2` ⇒ обобщённый семафор пускает в КС до 2 процессов одновременно.
`N = 4` ⇒ 4 процесса соревнуются, значит давление на семафор есть (4 > 2),
и проверка взаимного исключения нетривиальна.

### Глобальные переменные (`main.pml:8-15`)

```promela
byte S = 1;        // бинарный семафор-мьютекс для count
byte gate = 1;     // бинарный семафор-турникет
int  count = K;    // целочисл. компонент обобщённого семафора
byte critical = 0; // счётчик процессов в КС — ТОЛЬКО для верификации
```

- `S`, `gate` — два **бинарных** семафора из формулировки задания.
- `count` — стартует с `K`, реализует «сколько слотов осталось» (Лемма 6.6:
  `count = k − #inCS`).
- `critical` — не часть алгоритма Барца. Это «датчик» для LTL: процессы
  увеличивают его на входе в КС и уменьшают на выходе, а свойство `mutex`
  следит, что он не превысит `K`. Аналог приёма из Listing 6.1 Бен-Ари, где
  используется переменная `critical` и `assert(critical <= K)`.

### Макросы семафора (`main.pml:20-21`)

Разобраны в §7. Параметр макроса называется `s` (строчная), глобальные
семафоры — `S` и `gate`; коллизии имён нет.

### Процесс (`main.pml:25-58`)

```promela
proctype process(byte id) {
    do
    :: true ->
        skip;                 // некритическая секция
        ... вход (p1..p6) ...
        ... КС ...
        ... выход (p7..p11) ...
    od;
}
```

- `proctype process(byte id)` — тип процесса; `id` оставлен для
  совместимости со стилем `part-1` (там `worker(byte id)`), сам алгоритм
  Барца симметричен и `id` не использует.
- `do :: true -> ... od` — «loop forever» из листинга 6.13: процесс
  бесконечно повторяет цикл «некритическая секция → вход → КС → выход».
- `skip` — модель «некритической секции»: процесс что-то делает вне КС.

### Протокол входа — симуляция `wait` (`main.pml:33-40`)

```promela
wait(gate);                   // p1
wait(S);                      // p2
count = count - 1;            // p3
if
:: count > 0 -> signal(gate); // p4, p5
:: else -> skip;
fi;
signal(S);                    // p6
```

Дословное соответствие листингу 6.13:

| Строка `main.pml` | Шаг Барца | Что делает |
|---|---|---|
| `wait(gate)` (33) | p1 | пройти турникет (за раз — один процесс) |
| `wait(S)` (34) | p2 | захватить мьютекс на `count` |
| `count = count - 1` (35) | p3 | занять один слот обобщённого семафора |
| `if count > 0 -> signal(gate)` (37) | p4–p5 | слоты ещё есть → пропустить следующего |
| `:: else -> skip` (38) | p4 (ложь) | слотов нет → турникет **не** открываем (остаётся 0) |
| `signal(S)` (40) | p6 | отпустить мьютекс |

Ключевой момент — ветка `else`: когда `count` после декремента стал `0`,
`signal(gate)` **не выполняется**, `gate` остаётся `0`, и следующий процесс
**заблокируется на `wait(gate)`** (`p1`). Так турникет «закрывается» ровно
тогда, когда все `K` слотов заняты.

### Критическая секция (`main.pml:45-47`)

```promela
critical++;
assert(critical <= K);
critical--;
```

Это «тело» КС. `critical++/--` — датчик присутствия в КС. `assert(critical
<= K)` — локальная проверка взаимного исключения прямо во время симуляции и
верификации (если когда-либо в КС окажется > `K` процессов, SPIN выдаст
*assertion violated* с контрпримером). Дублирует по смыслу `ltl mutex`, но
ловится и в режиме симуляции.

### Протокол выхода — симуляция `signal` (`main.pml:50-56`)

```promela
wait(S);                       // p7
count = count + 1;             // p8
if
:: count == 1 -> signal(gate); // p9, p10
:: else -> skip;
fi;
signal(S);                     // p11
```

| Строка `main.pml` | Шаг Барца | Что делает |
|---|---|---|
| `wait(S)` (50) | p7 | захватить мьютекс на `count` |
| `count = count + 1` (51) | p8 | освободить слот (вышли из КС) |
| `if count == 1 -> signal(gate)` (53) | p9–p10 | слотов было 0, стал 1 → открыть турникет одному ждущему |
| `:: else -> skip` (54) | p9 (ложь) | турникет и так открыт — повторно не открываем |
| `signal(S)` (56) | p11 | отпустить мьютекс |

Условие `count == 1` критично: `signal(gate)` делается **только** при
переходе `count` `0 → 1`. Это гарантирует, что на каждое «закрытие» турникета
(во входе, когда `count` дошёл до 0) приходится **ровно одно** «открытие» —
поэтому `gate` никогда не станет 2 (Лемма 6.5(6), наш `ltl bingate`).

### Запуск процессов (`main.pml:60-71`)

```promela
init {
    byte proc_id = 0;
    atomic {
        do
        :: proc_id < N -> run process(proc_id); proc_id = proc_id + 1;
        :: proc_id == N -> break;
        od;
    }
}
```

`init` — стартовый процесс. В `atomic`-блоке (чтобы запуск не чередовался)
создаётся `N = 4` экземпляра `process`. Стиль (цикл `do :: cond -> ... ::
cond -> break od` и `atomic`-запуск через `run`) намеренно взят из
`part-1/main.pml` для единообразия.

## 9. Трасса выполнения: N=4, K=2

Покажем один сценарий, чтобы «увидеть» работу турникета. Состояние:
`(gate, S, count, в_КС)`. Старт: `gate=1, S=1, count=2, вКС=0`.

| # | Действие | gate | S | count | в КС | Комментарий |
|---|---|---|---|---|---|---|
| 0 | старт | 1 | 1 | 2 | 0 | 2 свободных слота |
| 1 | A: p1 wait(gate) | 0 | 1 | 2 | 0 | A прошёл турникет, закрыл его |
| 2 | A: p2 wait(S) | 0 | 0 | 2 | 0 | A под мьютексом |
| 3 | A: p3 count-- | 0 | 0 | 1 | 0 | занял слот |
| 4 | A: p4 `count>0`→p5 signal(gate) | 1 | 0 | 1 | 0 | слот ещё есть → пускаем следующего |
| 5 | A: p6 signal(S) | 1 | 1 | 1 | 0 | A отпустил мьютекс |
| 6 | A: вход в КС (critical++) | 1 | 1 | 1 | 1 | A в КС |
| 7 | B: p1 wait(gate) | 0 | 1 | 1 | 1 | B прошёл, закрыл турникет |
| 8 | B: p2 wait(S) | 0 | 0 | 1 | 1 | |
| 9 | B: p3 count-- | 0 | 0 | 0 | 1 | занят **последний** слот |
| 10 | B: p4 `count>0` ложно → else | 0 | 0 | 0 | 1 | турникет **остаётся 0** |
| 11 | B: p6 signal(S) | 0 | 1 | 0 | 1 | |
| 12 | B: вход в КС | 0 | 1 | 0 | 2 | **2 процесса в КС = K** |
| 13 | C: p1 wait(gate) | — | — | 0 | 2 | `gate=0` → C **БЛОКИРОВАН** |
| 14 | D: p1 wait(gate) | — | — | 0 | 2 | D тоже блокирован |
| 15 | A: critical-- (выход из КС, `main.pml:47`) | 0 | 1 | 0 | 1 | A покинул КС (до p7!) |
| 16 | A: p7 wait(S) | 0 | 0 | 0 | 1 | A захватил мьютекс на count |
| 17 | A: p8 count++ | 0 | 0 | 1 | 1 | слот освободился |
| 18 | A: p9 `count==1`→p10 signal(gate) | 1 | 0 | 1 | 1 | открыли турникет одному |
| 19 | A: p11 signal(S) | 1 | 1 | 1 | 1 | A отпустил мьютекс |
| 20 | C: p1 wait(gate) разблокирован | 0 | 1 | 1 | 1 | C наконец прошёл |

Видно главное:

- В строке 12 в КС ровно `K = 2` процесса — больше турникет не пускает
  (`mutex` держится).
- Строки 13–14: лишние процессы честно ждут на `p1` (`gate = 0`).
- `gate` всё время только 0 или 1 (`bingate`), `S` тоже (`binsem`).
- `count` точно равен `K − (в КС)` в моменты вне «узкого места» — Лемма 6.6.

Это лишь один путь; SPIN проверяет **все** возможные чередования.

## 10. LTL-свойства модели

LTL (Linear Temporal Logic) позволяет говорить о том, что верно **во
времени** на всех вычислениях. Два класса свойств:

- **Безопасность (safety)** — «ничего плохого не случится никогда»,
  формально `[] (хорошо)`. Нарушается конечным контрпримером.
- **Живость (liveness)** — «что-то хорошее когда-нибудь случится»,
  формально `<> (хорошо)` / `[]<>(...)`. Нарушается бесконечным
  контрпримером (зависанием).

Наши формулы (`main.pml:76-86`):

```promela
ltl mutex    { [] (critical <= K) }   // безопасность — главное свойство
ltl bingate  { [] (gate <= 1) }       // безопасность — gate бинарный
ltl binsem   { [] (S <= 1) }          // безопасность — S бинарный
ltl liveness { [] <> (critical > 0) } // живость — система прогрессирует
```

- **`mutex`** — формализация Теоремы 6.7: в любом состоянии любого вычисления
  в КС не более `K` процессов. Это то, ради чего вообще нужен алгоритм.
- **`bingate`** — формализация Леммы 6.5(6) (`[]bingate` у Бен-Ари): `gate`,
  хоть и объявлен обычной `byte`-переменной, фактически **бинарный**.
  Доказывает, что мы и правда симулируем обобщённый семафор
  *бинарными* — выполняем условие задания.
- **`binsem`** — то же для `S`: мьютекс остаётся бинарным.
- **`liveness`** — `[] <> (critical > 0)`: «всегда найдётся момент в будущем,
  когда кто-то в КС». Означает, что система не зависает в дедлоке и
  продолжает прогресс (турникет не закрывается навсегда).

Почему в формулах есть `[]`: без него свойство проверялось бы только в
начальном состоянии. `[] (critical <= K)` требует выполнения во **всех**
состояниях всего вычисления — это и есть настоящая безопасность.

## 11. Полный разбор вывода `make run`

`make run` (см. `part-2/Makefile`) делает по шагам: `spin -a main.pml &&
gcc -w -o pan pan.c` (генерация + сборка верификатора), затем **четыре**
прогона `./pan -a -N <claim>` (последний — с `-f`). Разберём вывод по
блокам.

### 11.1 Генерация верификатора (вывод `spin -a`)

```
Verifying Main in Spin CLI...
ltl mutex: [] ((critical<=2))
ltl bingate: [] ((gate<=1))
ltl binsem: [] ((S<=1))
ltl liveness: [] (<> ((critical>0)))
  the model contains 4 never claims: liveness, binsem, bingate, mutex
  only one claim is used in a verification run
  choose which one with ./pan -a -N name (defaults to -N mutex)
  or use e.g.: spin -search -ltl mutex main.pml
```

- `Verifying Main in Spin CLI...` — это `echo` из Makefile.
- 4 строки `ltl ...:` — `spin -a` печатает каждую формулу **после раскрытия
  макросов**: видно `critical<=2`, то есть `#define K 2` уже подставлен.
  Подтверждение, что формулы распознаны и скомпилированы.
- `the model contains 4 never claims` — на каждую `ltl{}` SPIN сгенерировал
  свой **never claim** (автомат-наблюдатель), все 4 попали в `pan.c`.
- `only one claim is used in a verification run` — за один запуск `pan`
  проверяется **ровно одно** свойство. Поэтому Makefile вызывает `pan`
  четыре раза с разным `-N имя`. Без `-N` взялся бы `mutex` (defaults).

### 11.2 Шапка прогона (на примере `mutex`)

```
pan: ltl formula mutex

(Spin Version 6.5.2 -- 18 September 2025)
        + Partial Order Reduction
```

- `pan: ltl formula mutex` — какая формула сейчас активна.
- `+ Partial Order Reduction` — включена **редукция частичных порядков**:
  оптимизация, отбрасывающая эквивалентные перестановки независимых шагов
  разных процессов. Результат верификации не меняет, но резко уменьшает
  число состояний (поэтому у нас ~1728 состояний, а не экспоненциально
  больше). Это та «галочка про редукцию частичного порядка», о которой
  говорят на лекции.

### 11.3 Что именно проверяется

```
Full statespace search for:
        never claim             + (mutex)
        assertion violations    + (if within scope of claim)
        acceptance   cycles     + (fairness disabled)
        invalid end states      - (disabled by never claim)
```

- `Full statespace search` — **исчерпывающий** перебор (режим exhaustive из
  лекции), не bitstate/hash-compact: проверяются ВСЕ достижимые состояния.
- `never claim + (mutex)` — активен never claim `mutex` (`+` = включено).
- `assertion violations + (if within scope of claim)` — `assert(critical
  <= K)` (`main.pml:46`) проверяется, но только на путях, согласованных с
  активным never claim («в области видимости claim»).
- `acceptance cycles + (fairness disabled)` — pan дополнительно ищет циклы
  через допускающие состояния (механизм проверки живости). Для safety это
  безвредно. `fairness disabled` — без предположения справедливости.
- `invalid end states - (disabled by never claim)` — **ВАЖНО**: при
  активном never claim проверка тупиков выключена (`-`). Поэтому
  отсутствие дедлока проверяем отдельным прогоном **без** claim (§11.8).

### 11.6 Блок `unreached` — то, что вас смутило

```
unreached in proctype process
        main.pml:58, state 34, "-end-"
        (1 of 34 states)
unreached in init
        (0 of 10 states)
unreached in claim mutex
        _spin_nvr.tmp:8, state 10, "-end-"
        (1 of 10 states)
```

SPIN компилирует **каждый** процесс и **каждый** never claim в конечный
автомат с пронумерованными управляющими состояниями (по одному на «точку
между операторами»). После верификации он сообщает, какие из этих
состояний **ни разу не были достигнуты** — чтобы вы заметили мёртвый код.
Разберём все три блока.

**`unreached in proctype process` → `main.pml:58, state 34, "-end-"
(1 of 34 states)`**

- Тело `proctype process` развернулось в автомат из **34** управляющих
  состояний.
- Не достигнуто **ровно 1** — состояние №34 с меткой `"-end-"`, привязанное
  к `main.pml:58` (закрывающая `}` процесса).
- `"-end-"` — это неявное **конечное** состояние процесса: точка сразу после
  тела, куда процесс попал бы, **завершившись**.
- Наш процесс — `do :: true -> ... od` (`main.pml:27-57`) — **бесконечный
  цикл без `break`**. Управление никогда не доходит до `}`. Значит `-end-`
  **недостижимо by design**.
- Это **НЕ ошибка и НЕ мёртвый код**: для любого реактивного процесса
  «loop forever» терминатор недостижим всегда. SPIN обязан о нём сообщить
  (он не знает, что бесконечность тут намеренная), но для нас это ожидаемо.
  На лекции про это прямо говорят: можно снять галочку «report unreachable
  code», и такие `-end-` пропадут.
- `unreached in init (0 of 10 states)` — наоборот: **все 10** состояний
  `init` достигнуты, `init` нормально доработал до конца (запустил 4
  процесса и завершился). Мёртвого кода в `init` нет.

**`unreached in claim mutex` → `_spin_nvr.tmp:8, state 10, "-end-"
(1 of 10 states)` — почему «1 of 10» и что это значит**

Ключевой вопрос. По шагам:

1. **Что такое never claim.** Для свойства φ SPIN строит автомат Бюхи,
   распознающий ровно те вычисления, которые φ **нарушают** (то есть
   автомат для **¬φ**). Это и есть *never claim* — «так быть НЕ должно».
   Его исходник SPIN кладёт во временный файл `_spin_nvr.tmp` (и в `pan.c`).
2. **Как он работает.** Верификатор гоняет систему и never claim
   **синхронно**. Если удаётся загнать never claim в его принимающее/
   конечное состояние одновременно с реальным вычислением системы — найден
   контрпример к φ: тогда было бы `errors: 1+` и файл `.trail`.
3. **Структура автомата.** Never claim для `mutex` (= `[](critical<=2)`,
   его отрицание — `<>(critical>2)`) скомпилирован в **10** управляющих
   состояний. Среди них финальное `"-end-"` — состояние №10
   (`_spin_nvr.tmp:8`), достижение которого означало бы
   «нарушение зафиксировано».
4. **Что значит «1 of 10 unreached».** Остальные **9** состояний автомата-
   наблюдателя были достигнуты — claim всё время «следил» за системой, на
   каждом шаге проверяя «а не нарушилось ли `critical<=2`?». Но в его
   терминал `"-end-"` (state 10) поиск **ни разу не смог попасть** ни на
   одном из 1728 состояний и 4409 переходов.
5. **Вывод.** Недостижимость `"-end-"` у never claim — это **именно то, что
   мы хотим**: верификатор перебрал всё пространство и **не нашёл ни одного
   пути** к нарушению. Поэтому строка согласована с `errors: 0`. Если бы
   `"-end-"` claim'а оказалось достижимым — было бы `errors: 1` и
   контрпример.

> Коротко: **«1 of N unreached в claim» при `errors: 0` — это и есть
> доказательство, что свойство держится** (нарушающее состояние автомата-
> ловушки недостижимо). Хороший знак, а не предупреждение.

### 11.7 Чем отличается прогон `liveness`

```
        acceptance   cycles     + (fairness enabled)
...
State-vector 60 byte, depth reached 1806, errors: 0
     2441 states, stored (7118 visited)
     7048 states, matched
    14166 transitions (= visited+matched)
...
unreached in claim liveness
        _spin_nvr.tmp:37, state 13, "-end-"
        (1 of 13 states)
```

- `fairness enabled` — потому что Makefile запускает `liveness` с флагом
  `-f` (слабая справедливость). У safety-свойств было `fairness disabled`.
- `2441 states, stored (7118 visited)` — для liveness pan использует
  **вложенный (nested) DFS**: каждое состояние может посещаться дважды
  (внешний поиск + внутренний поиск цикла), поэтому `visited` (7118) >
  `stored` (2441), и `transitions = visited + matched`, а не
  `stored + matched`.
- `claim liveness` имеет **13** состояний (а не 10): автомат Бюхи для
  `[]<>(critical>0)` (свойство-«повторяемость», recurrence) сложнее, чем
  для простого инварианта. Логика та же: `"-end-"` (state 13) недостижим →
  `1 of 13 unreached` → `errors: 0` → живость держится.
- `_spin_nvr.tmp:8 / :17 / :26 / :37` — это просто строки в сгенерированном
  файле never-claim'ов, где лежит финал каждого из 4 автоматов
  (mutex/bingate/binsem/liveness). Номера разные, потому что 4 claim'а
  идут друг за другом в одном файле.

### 11.8 Отдельная проверка на дедлок

Поскольку при активном never claim `invalid end states` отключены (§11.3),
отсутствие тупиков проверяется **без** claim — на модели без `ltl`:

```
Full statespace search
        assertion violations    +
        invalid end states      +
State-vector 52 byte, depth reached 909, errors: 0
```

`invalid end states +` включён и `errors: 0` ⇒ тупиковых (заблокированных
навсегда) состояний нет, `assert(critical <= K)` ни разу не сработал.
(State-vector тут меньше — 52 байта — потому что без автомата-наблюдателя
состояние системы компактнее.) Алгоритм Барца в нашей модели **корректен
и без дедлоков**.

### 11.9 Итоговая сводка `make run`

| Свойство | Тип | состояний claim | финал `-end-` | errors |
|---|---|---|---|---|
| `mutex` `[](critical<=2)` | безопасность (инвариант) | 10 | 1 of 10 unreached | 0 |
| `bingate` `[](gate<=1)` | безопасность | 10 | 1 of 10 unreached | 0 |
| `binsem` `[](S<=1)` | безопасность | 10 | 1 of 10 unreached | 0 |
| `liveness` `[]<>(critical>0)` | живость (recurrence) | 13 | 1 of 13 unreached | 0 |

Везде `errors: 0`. Единственное «недостижимое» в `process` — `-end-`
бесконечного цикла (норма). Единственное «недостижимое» в каждом claim —
его терминал-ловушка, и это **признак, что нарушения нет**.

## 12. Ограничение алгоритма Барца

Важно понимать, **что именно** доказано. Теорема 6.7 у Бен-Ари — это только
**взаимное исключение** (`#inCS ≤ k`). Алгоритм Барца **не гарантирует
свободу от голодания**: при слабых (weak) семафорах возможен сценарий, где
конкретный процесс бесконечно «оттирается» от турникета другими и никогда не
войдёт в КС. Именно поэтому сразу за §6.10 в книге идёт §6.11 — алгоритм
**Уддинга** (Udding, 6.14), специально свободный от голодания.

Поэтому наш `ltl liveness` намеренно сформулирован **слабо**: `[] <>
(critical > 0)` — «система в целом прогрессирует» (нет глобального дедлока),
а **не** «каждый процесс рано или поздно войдёт в КС». Сильную
индивидуальную живость для Барца доказать нельзя — это его принципиальное
свойство, а не недочёт модели.

`make run` (см. `part-2/Makefile`) выполняет:

1. `spin -a main.pml && gcc -w -o pan pan.c` — сгенерировать и собрать
   верификатор;
2. `./pan -a -N mutex` — взаимное исключение (главное свойство);
3. `./pan -a -N bingate` — `gate` бинарный;
4. `./pan -a -N binsem` — `S` бинарный;
5. `./pan -a -f -N liveness` — живость (флаг `-f` — слабая справедливость).

Ожидаемый результат по каждому пункту — `errors: 0`.
