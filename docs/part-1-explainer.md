## 1. Задание (Вариант 1.4)

Из `part-1/TASK.md` дословно:

> Разработайте параллельный алгоритм умножения двух матриц n×n для P процессов
> так, чтобы параллельно вычислялись строки результирующей матрицы. Исходные
> матрицы загружены на процессы заранее. Сформулировать свойства алгоритма на
> языке LTL. Обмен данными, если он необходим, осуществляется с помощью

Расшифровка по словам — это чек-лист того, что обязано быть в коде:

| Требование задания | Где в `main.pml` |

| «для P процессов» | `#define P 2`, `run worker(...)` ×P (`main.pml:4,130-138`) |
| «параллельно вычислялись **строки**» | каждый `worker(id)` берёт строки `id, id+P, id+2P, …` (`main.pml:21,54`) |
| «матрицы загружены **заранее**» | `init` жёстко задаёт `A`,`B` до запуска воркеров (`main.pml:117-123`) |
| «обмен данными — **каналами**» | `chan row_computed`, операции `!` / `?` (`main.pml:16,48,81`) |
| «**0-й процесс** выводит результат» | блок `if :: id == 0 -> … printf …` (`main.pml:59-110`) |
| «свойства на **LTL**» | `ltl liveness`, `ltl safety` (`main.pml:142,145-147`) |

В нашей модели зафиксировано `N = 3` (матрица 3×3) и `P = 2` (два рабочих
процесса). 3 строки на 2 процесса — нагрузка несимметрична (один процесс
получает 2 строки, другой 1), поэтому проверка нетривиальна: канал реально
используется.

## 2. Ликбез: зачем нужна формальная верификация

Есть два разных понятия «правильности»:

- **Синтаксически правильная** — компилятор/`spin` не ругается на текст.
- **Семантически правильная (корректная)** — программа делает **именно то,
  что должна**.

Ключевой тезис (Ю. Г. Карпов):

> *Вопрос о корректности программы не имеет смысла, пока не сказано, ЧТО
> программа ДОЛЖНА делать.*

Итог: **корректность = соответствие требованиям**. Нет требований — нет
корректности. Поэтому задание и требует «сформулировать свойства на LTL»: LTL —
это и есть формальная запись того, «что программа должна делать».

Почему для **параллельной** задачи мало тестов: шаги `worker(0)` и `worker(1)`
чередуются (interleaving) огромным числом способов. Тест прогоняет **одно**
чередование. Верификация (model checking) перебирает **все** чередования и
доказывает свойство для каждого. Для умножения матриц это критично: запись в
канал и чтение из него у двух процессов могут переплестись по-разному, и нужно
гарантировать корректный результат **при любом** переплетении.

## 3. Ликбез: что такое SPIN и Promela

**SPIN** (Simple Promela INterpreter) — инструмент формальной верификации
(Bell Labs, с 1996; премия ACM System Award 2001; применялся в NASA Mars
Exploration Rovers, управлении шлюзами Роттердама).

SPIN умеет три вещи:

1. строить модель параллельной системы на языке **Promela**;
2. выражать требования к ней на **LTL** (Linear Temporal Logic);
3. автоматически доказывать, что модель удовлетворяет требованиям
   (**model checking**).

**Promela** (Protocol Meta Language) — язык **моделирования**, а не
программирования: программа на Promela не запускается на процессоре, она
описывает формальную модель (абстракцию). Ключевые ограничения, важные именно
для верификации:

- все переменные имеют **конечную** область значений (иначе пространство
  состояний бесконечно);
- функций нет — только **процессы** (`proctype`);
- параллельность — основа языка, а не исключение.

## 4. Основы синтаксиса Promela — по нашему коду

Этого раздела достаточно, чтобы прочитать `main.pml` целиком. Каждый пункт
проиллюстрирован строкой из нашего файла.

### 4.1 Константы: `#define` (`main.pml:1-4`)

```promela
#define N 3   // размер квадратных матриц N*N
#define P 2   // число параллельных процессов
```

Работает как C-препроцессор: SPIN прогоняет `.pml` через `cpp`, поэтому
`#define`, `#include`, `#ifdef` доступны. Везде, где встретится `N`,
подставится `3`. Это **текстовая** подстановка: в LTL-формуле `C[0] == 43`
число `43` останется числом, а вот `N*N` развернётся в `3*3`.

### 4.2 Переменные и типы (`main.pml:7-12`)

```promela
int A[N * N];        // массив из 9 элементов типа int
int B[N * N];
int C[N * N];
bool done = false;
```

| Тип    | Размер | Диапазон |
|--------|--------|----------|
| `bit`  | 1 бит  | 0 / 1 |
| `bool` | 1 бит  | false / true |
| `byte` | 8 бит  | 0 … 255 |
| `short`| 16 бит | −32 768 … 32 767 |
| `int`  | 32 бит | ≈ ±2,1 млрд |

Двумерных массивов в Promela нет — только одномерные. Поэтому матрица
хранится «плоско», а индексация ручная: элемент `(i, j)` лежит в
`C[i * N + j]` (см. `main.pml:37,45,83`). Тип `int` для `C` выбран потому, что
`test.py` гоняет элементы от −10 до 10 и произведения/суммы могут стать
отрицательными (у коллег с `byte` это не так — см. §12).

Глобальные переменные (`A`, `B`, `C`, `done`, `row_computed`) **видны всем
процессам**. Локальные переменные процесса (`row`, `col`, `k`, `sum` внутри
`worker`) видны только ему — и, важно, **недоступны в LTL-формулах** (§10).

### 4.3 Каналы: `chan` (`main.pml:16`)

```promela
chan row_computed = [N * N] of { byte, byte, int };
```

Канал — это **буферизованная FIFO-очередь сообщений** между процессами:

- `row_computed` — имя;
- `[N * N]` — глубина буфера (сюда влезает 9 сообщений);
- `of { byte, byte, int }` — тип одного сообщения: кортеж
  `{номер_строки, номер_столбца, значение}`.

Семантика блокировки — **ключ к синхронизации без общих переменных**:

- если буфер **полон**, отправитель (`!`) **блокируется**, пока кто-то не
  прочитает;
- если буфер **пуст**, получатель (`?`) **блокируется**, пока кто-то не
  отправит.

Особый случай — `chan c = [0] of {...}` — рандеву (синхронный канал):
отправитель и получатель проходят шаг одновременно. У нас буфер на 9 элементов
(`[N*N]`), так что `worker(1)` может сложить все свои элементы и не ждать.

### 4.4 Процессы: `proctype` и `init` (`main.pml:19,115`)

```promela
proctype worker(byte id) { ... }   // ТИП процесса (сам не запускается)
init { ... }                       // стартовый процесс, запускается автоматически
```

- `proctype` только **описывает**, как работает процесс; экземпляр создаётся
  через `run` (§4.9).
- `init` — особый процесс, который SPIN запускает сам при старте. У нас в нём
  загружаются матрицы и запускаются воркеры.
- `byte id` — параметр, **локальная копия** для каждого экземпляра. Именно
  через разные `id` процессы делят строки.

### 4.5 Цикл: `do … od` (`main.pml:26-56`)

Единственный цикл в Promela (синтаксис Дейкстры):

```promela
do
:: row < N  -> /* тело */  row = row + P;
:: row >= N -> break;
od;
```

Как работает:

1. SPIN смотрит на **все** ветки `:: guard -> …`;
2. из веток с **истинным** охранным условием **недетерминированно** выбирает
   одну и выполняет её;
3. возвращается к началу `do`;
4. `break` — выход;
5. если **ни одна** ветка не истинна — процесс **блокируется** (ждёт).

Поэтому `:: row >= N -> break` — это **условие выхода**, а не `else`. При
`<` и `>=` ветки взаимоисключающие, недетерминизма тут нет.

### 4.6 Ветвление: `if … fi` (`main.pml:43-49`)

```promela
if
:: id == 0 -> C[row * N + col] = sum;       // 0-й процесс пишет напрямую
:: id != 0 -> row_computed!row,col,sum;     // остальные шлют в канал
fi;
```

То же, что `do…od`, но без повтора: выбрать одну истинную ветку, выполнить,
выйти. Если ни одна не истинна — блокировка. Есть спец-ветка `else`
(срабатывает, когда все остальные ложны) — она используется в `main.pml:69`.

### 4.7 Отправка и приём: `!` и `?` (`main.pml:48,81`)

```promela
row_computed!row,col,sum;   // отправить кортеж в канал
row_computed?r,c,val;       // принять кортеж, разложив в переменные
```

- `!` — послать сообщение (поля через запятую);
- `?` — принять сообщение (поля пишутся в перечисленные переменные).

FIFO: что отправлено первым — принято первым. Это и есть «обмен данными с
помощью каналов» из задания.

### 4.8 Атомарность: `atomic {}` (`main.pml:131-138`)

```promela
atomic {
    do
    :: proc_id < P -> run worker(proc_id); proc_id = proc_id + 1;
    :: proc_id == P -> break;
    od;
}
```

Блок `atomic` выполняется **без чередования** с другими процессами — как одна
неделимая операция. Здесь это гарантирует, что оба воркера запустятся «разом»,
до того как кто-то из них начнёт работать (детерминированный старт, меньше
лишних состояний). У коллег `atomic` нужен ещё и для защиты счётчика от гонки —
см. §12.

### 4.9 Запуск процессов: `run` (`main.pml:134`)

```promela
run worker(proc_id);
```

`run` создаёт **экземпляр** процесса с переданными параметрами и пускает его
параллельно (SPIN начнёт чередовать его шаги с остальными). Возвращает pid.
Без `run` `proctype` — просто «чертёж», ничего не исполняющий.

### 4.10 Охраняемая инструкция (executability)

Фундаментальное свойство Promela: **любое булево выражение само по себе —
оператор**, который *исполним* только когда истинен, иначе **блокирует**
процесс. Это и стоит за каждой веткой `::`. У нас это работает в каналах
(`row_computed?…` блокируется на пустом канале, `main.pml:81`), а у коллег —
напрямую: строка `finished == P;` (`friends-main.pml:46`) — это «жди, пока
счётчик не дорастёт до P» (§12).

## 5. Как наш `main.pml` решает Вариант 1.4

Идея распределения строк (это и есть «параллельно вычисляются строки»):

- `worker(id)` начинает со строки `row = id` и идёт с шагом `P`
  (`main.pml:21,54`): `id, id+P, id+2P, …`.
- При `N = 3, P = 2`:
  - `worker(0)` → строки `0`, `2` (потом `4 ≥ 3` → стоп);
  - `worker(1)` → строка `1` (потом `3 ≥ 3` → стоп).

Кто куда пишет (`main.pml:43-49`):

- **`worker(0)`** свои строки (0 и 2) считает и **сразу кладёт в `C`**
  напрямую — он же и есть «нулевой процесс»;
- **`worker(1)`** строку 1 считает и **отправляет в канал** `row_computed`
  по элементу: `{1, col, значение}`.

Сборка и вывод — только `worker(0)` (`main.pml:59-110`):

1. считает, сколько элементов придёт по каналу (`expected_elements`): для
   каждой строки `i`, не принадлежащей нулевому процессу (`i % P != 0`),
   добавляет `N` элементов (`main.pml:65-73`). При N=3,P=2 это строка 1 →
   `expected_elements = 3`;
2. в цикле читает ровно столько кортежей из канала и раскладывает их в `C`
   (`main.pml:79-86`);
3. печатает матрицу `C` (`main.pml:89-107`);
4. ставит `done = true` (`main.pml:110`) — **последнее** действие.

Поэтому `done == true` ⇒ «все элементы `C` уже на местах и корректны». Это и
позволяет писать LTL через `done` (§10).

## 6. Разбор `main.pml` строка за строкой

### Шапка: константы, данные, канал (`main.pml:1-16`)

```promela
#define N 3                                       // 1-2: размер матриц
#define P 2                                       // 3-4: число процессов
int A[N * N]; int B[N * N]; int C[N * N];          // 7-9: плоские матрицы 9 эл-тов
bool done = false;                                 // 12: флаг для LTL
chan row_computed = [N * N] of { byte,byte,int };  // 16: канал {строка,столбец,значение}
```

`done` — не часть алгоритма умножения, это **датчик для верификатора**
(аналог приёма с `critical` в части 2): единственная глобальная булева
переменная, по которой LTL понимает «вычисление завершено».

### Воркер: подготовка (`main.pml:19-23`)

```promela
proctype worker(byte id) {
    byte row = id;     // 21: первая «моя» строка = id
    byte col, k;       // 22: индекс столбца и индекс свёртки
    int  sum;          // 23: накопитель скалярного произведения
```

`row` инициализируется параметром `id` — так процессы и делят строки без
всякой синхронизации (распределение задаётся арифметикой, не каналом).

### Тройной цикл умножения (`main.pml:26-56`)

```promela
do
:: row < N ->                                  // 27: пока есть «моя» строка
    col = 0;
    do
    :: col < N ->                              // 31: по столбцам B
        sum = 0; k = 0;
        do
        :: k < N ->                            // 36: свёртка строки A и столбца B
            sum = sum + A[row*N + k] * B[k*N + col];  // 37
            k = k + 1;
        :: k == N -> break;                    // 39
        od;
        if
        :: id == 0 -> C[row*N + col] = sum;    // 44-45: 0-й пишет напрямую
        :: id != 0 -> row_computed!row,col,sum;// 47-48: остальные — в канал
        fi;
        col = col + 1;                         // 50
    :: col == N -> break;                      // 51
    od;
    row = row + P;                             // 54: к следующей «моей» строке
:: row >= N -> break;                          // 55
od;
```

Три вложенных `do…od` — это классические три цикла матричного умножения
(`row`, `col`, `k`). Ветвление в `main.pml:43-49` — то самое место, где
требование «обмен каналами» материализуется: `worker(1)` физически не пишет
в `C`, он только шлёт `row_computed!1,col,sum`.

### Сборка нулевым процессом (`main.pml:59-86`)

```promela
if
:: id == 0 ->
    int i, j;
    int expected_elements = 0;
    i = 0;
    do
    :: i < N ->                                // 65-73: сколько ждать из канала
        if
        :: (i % P) != 0 -> expected_elements = expected_elements + N;  // 68
        :: else -> skip;                       // 69
        fi;
        i = i + 1;
    :: i == N -> break;
    od;

    int received = 0; byte r, c; int val;
    do
    :: received < expected_elements ->         // 80
        row_computed?r,c,val;                  // 81: блокируется, пока канал пуст
        C[r*N + c] = val;                      // 83: разложить в C
        received = received + 1;
    :: received == expected_elements -> break; // 85
    od;
```

Логика подсчёта `expected_elements`: строки, где `i % P == 0`, считает сам
`worker(0)` (он их уже записал напрямую), а строки с `i % P != 0` придут по
каналу — по `N` элементов на строку. При N=3,P=2: только `i = 1` даёт
`+N`, итого `expected_elements = 3`. Цикл `main.pml:79-86` ровно 3 раза
делает блокирующий `row_computed?…` (§4.3/§4.10) — это и есть синхронизация
«дождаться данных от воркера».

### Вывод и флаг (`main.pml:89-112`)

```promela
    printf("Result Matrix C:\n");              // 89-107: печать матрицы 3x3
    ... вложенные do для строк/столбцов с запятыми ...
    done = true;                               // 110: ПОСЛЕДНЕЕ действие 0-го
:: id != 0 -> skip;                            // 111: остальные ничего не печатают
fi;
}
```

`done = true` стоит **после** печати и сборки — это гарантирует
интерпретацию «`done` ⇒ `C` готова».

### `init`: загрузка данных и старт (`main.pml:115-139`)

```promela
init {
    A[0]=5; A[1]=3; A[2]=7;   // 117  строка 0 матрицы A
    A[3]=1; A[4]=4; A[5]=0;   // 118  строка 1
    A[6]=3; A[7]=9; A[8]=1;   // 119  строка 2
    B[0]=3; B[1]=8; B[2]=7;   // 121
    B[3]=7; B[4]=2; B[5]=1;   // 122
    B[6]=1; B[7]=9; B[8]=1;   // 123
    // ожидаемый C: [43,109,45] [31,16,11] [73,51,31]  (комментарий 125-127)
    int proc_id = 0;
    atomic {                                   // 131-138: атомарный старт P воркеров
        do
        :: proc_id < P -> run worker(proc_id); proc_id = proc_id + 1;
        :: proc_id == P -> break;
        od;
    }
}
```

«Матрицы загружены заранее» из задания = строки 117–123: `init` заполняет
`A` и `B` **до** `run worker(...)`. Воркеры стартуют, когда данные уже на
месте.

### LTL-свойства (`main.pml:142-147`)

ltl liveness { <> (done == true) }
ltl safety  { [] (done -> (C[0]==43 && C[1]==109 && C[2]==45 &&

## 7. Трасса выполнения: N=3, P=2

Один конкретный сценарий, чтобы «увидеть» работу канала. Состояние:
`(канал: сколько сообщений в буфере, C-готовых-строк, done)`.

| # | Кто | Действие | Канал | Комментарий |
|---|---|---|---|---|
| 0 | init | загрузил A,B; `atomic` запустил worker(0), worker(1) | пуст | старт |
| 1 | worker(1) | строка 1: посчитал `C[3]=31`, `row_computed!1,0,31` | 1 | элемент ушёл в буфер |
| 2 | worker(0) | строка 0: `C[0]=43` напрямую (`id==0`) | 1 | в `C` записана ячейка 0 |
| 3 | worker(1) | `row_computed!1,1,16` | 2 | |
| 4 | worker(0) | `C[1]=109`, `C[2]=45` (доделал строку 0) | 2 | строка 0 матрицы C готова |
| 5 | worker(1) | `row_computed!1,2,11`; затем `row=3 ≥ N` → выход, `skip` | 3 | worker(1) **завершился** |
| 6 | worker(0) | строка 2: `C[6]=73`, `C[7]=51`, `C[8]=31` | 3 | строки 0 и 2 готовы |
| 7 | worker(0) | посчитал `expected_elements = 3` (только `i=1`) | 3 | |
| 8 | worker(0) | `row_computed?r,c,val` → `C[3]=31` | 2 | принял 1-й элемент |
| 9 | worker(0) | `?` → `C[4]=16` | 1 | |
| 10 | worker(0) | `?` → `C[5]=11`; `received == 3` → выход | 0 | строка 1 собрана |
| 11 | worker(0) | `printf` всей матрицы C | 0 | печать результата |
| 12 | worker(0) | `done = true` | 0 | **завершение зафиксировано** |

Важное:

- Шаги worker(0) и worker(1) на самом деле **чередуются** произвольно (порядок
  1↔2, 3↔4 и т.д. SPIN перебирает во всех вариантах) — здесь показан лишь
  один путь.
- Если бы worker(0) добрался до `row_computed?` (шаг 8) **раньше**, чем
  worker(1) что-то отправил, он бы **заблокировался** на пустом канале
  (§4.3) и ждал — взаимная блокировка-ожидание и есть синхронизация.
- На всех путях `done` в итоге становится `true` (это и докажет `liveness`),
  и в каждом состоянии с `done==true` матрица `C` именно `[43,109,45;
  31,16,11; 73,51,31]` (это докажет `safety`).

SPIN проверяет **все** такие трассы, а не одну.

## 8. Структура Крипке — формальная основа верификации

Каждая Promela-модель неявно задаёт **структуру Крипке**:

- **состояния** = все значения всех переменных + счётчики команд (PC) всех
  процессов;
- **переходы** = каждый исполнимый оператор;
- **начальное состояние** = старт `init`.

Для нашей модели «состояние» — это `(A, B, C, done, содержимое канала, PC
init, PC worker(0), PC worker(1))`. Отсюда и большой размер вектора состояния
(ниже в §11 увидим **292 байта**: 27 `int` в трёх массивах + буфер канала + PC
трёх процессов).

- **Симуляция** SPIN проходит **один** путь по этому графу.
- **Верификация** обходит **весь** граф — все чередования сразу.

Пример из лекции: два процесса, конкурентно делающие `x = x + 1`, без защиты
дают `x = 16` вместо 20 из-за гонки. У нас гонки на `C` **нет** именно потому,
что `worker(1)` не пишет в `C`, а шлёт в канал, а пишет в `C` только
`worker(0)` (единственный писатель). Это архитектурно исключает race condition —
в отличие от варианта коллег, где писателей в `C` несколько (§12).

## 9. LTL: темпоральная логика, операторы, safety/liveness

Классическая логика работает со **статичными** утверждениями. Но параллельная
программа меняется во времени: «сообщение в канале появится на выходе» неверно
в момент отправки (на выходе его ещё нет) — оно станет истинным **потом**.

**LTL** (Linear Temporal Logic) добавляет модальные операторы о том, что
происходит *потом / всегда / когда-нибудь* на бесконечной последовательности
состояний (вычислении).

| Spin | Теория | Читается | Смысл |
|------|--------|----------|-------|
| `<>` | F | eventually | когда-нибудь наступит |
| `[]` | G | always | верно в каждом состоянии |
| `U`  | U | until | p верно, пока не станет q (q обязательно будет) |
| `->` | → | implies | если … то (в данном состоянии) |
| `!`  | ¬ | not | отрицание |
| `&&` | ∧ | and | конъюнкция |
| `\|\|` | ∨ | or | дизъюнкция |

Связки: `<> p ≡ true U p`; `[] p ≡ !(<> !p)`.

Два класса требований:

- **Безопасность (safety)** — «ничего плохого **никогда** не случится»,
  формально `[] φ_good`. Нарушается **конечным** контрпримером (путь в
  «плохое» состояние).
- **Живость (liveness)** — «что-то хорошее **когда-нибудь** случится»,
  формально `<> φ_good`. Нарушается **бесконечным** контрпримером
  (зависание / livelock).

Почему нужны **оба**:

- одна `liveness` (`<> done`) — доказывает, что программа завершится, но
  ничего не говорит о правильности `C`;
- одна `safety` (`[] (done -> C верна)`) — формально истинна, даже если
  программа **никогда** не завершается (тогда `done` всегда `false`, и
  `false -> …` тривиально истинно);
- вместе: «программа **завершится** И результат будет **правильным**».

## 10. LTL-свойства нашей модели

### Шаг 0: что вообще можно использовать в LTL

LTL-формулы Promela ссылаются **только на глобальные** переменные. Локальные
`row, col, k, sum, i, j` внутри `worker` — недоступны. Глобальны: `A`, `B`,
`C`, `done`, канал `row_computed`. Из них:

- `A`, `B` заданы в `init` и не меняются — проверять нечего;
- `C` — результат, его и надо проверить;
- `done` — единственный признак «`C` готова» (см. §5).

### Шаг 1: откуда числа 43, 109, …

`init` (`main.pml:117-123`) задаёт
`A = [5,3,7; 1,4,0; 3,9,1]`, `B = [3,8,7; 7,2,1; 1,9,1]`. Эталон `C = A×B`
считается вручную один раз:

```
C[0]=5·3+3·7+7·1 = 43      C[1]=5·8+3·2+7·9 = 109     C[2]=5·7+3·1+7·1 = 45
C[3]=1·3+4·7+0·1 = 31      C[4]=1·8+4·2+0·9 = 16      C[5]=1·7+4·1+0·1 = 11
C[6]=3·3+9·7+1·1 = 73      C[7]=3·8+9·2+1·9 = 51      C[8]=3·7+9·1+1·1 = 31
```

Эти 9 чисел — прямо в формуле `safety`.

### Шаг 2: финальные формулы (`main.pml:142-147`)

```promela
ltl liveness { <> (done == true) }

ltl safety  { [] (done -> (C[0]==43 && C[1]==109 && C[2]==45 &&
                           C[3]==31  && C[4]==16  && C[5]==11 &&
                           C[6]==73  && C[7]==51  && C[8]==31)) }
```

- **`liveness`** `<> (done == true)` — «в **любом** вычислении `done` рано
  или поздно станет `true`». Гарантия отсутствия дедлока/зависания: канал не
  оставит `worker(0)` ждать вечно.
- **`safety`** `[] (done -> C верна)` — «во **всех** состояниях: если `done`
  уже `true`, то `C` содержит правильный результат». Оператор `[]` заставляет
  проверять это непрерывно, а не один раз.

### Шаг 3: почему `[]` обязателен (исторический урок проекта)

В истории git это место чинили (`fix: safety feature`). **Без** `[]`:

```promela
ltl safety { (done -> (...)) }   // ОШИБКА — проверка только в начальном состоянии
```

В начальном состоянии `done == false`, поэтому `false -> (...)` ≡ `true` —
формула тривиально истинна, верификатор сразу говорит «ок» и **фактически
ничего не проверяет** (характерный признак — `1 state, depth 0`, воркер даже
не запускался). Текущий код **корректен**: `[]` на месте (`main.pml:145`),
свойство проверяется во всех состояниях.

### Шаг 4: как SPIN это проверяет — never claim

SPIN проверяет не саму формулу, а её **отрицание**. На каждую `ltl{}` он
строит автомат Бюхи (**never claim**), принимающий ровно те вычисления,
которые формулу **нарушают**:

1. `spin -a main.pml` → `pan.c` + never claim'ы для `¬liveness` и `¬safety`.
2. `./pan -a -N liveness` — ищет путь, где `done` **никогда** не станет
   `true`. Нет такого пути → `errors: 0`.
3. Финальное состояние never claim с меткой `"-end-"` — это «нарушение
   зафиксировано». Если оно **недостижимо** → нарушений нет. Поэтому в
   корректном прогоне видно `1 of N states unreached` в `claim` — это
   **хороший знак**, а не предупреждение (детали в §11).

## 11. Полный разбор вывода: симуляция + верификация

`make run` (`part-1/Makefile:11-14`) делает:

```makefile
spin -T main.pml                                   # симуляция
spin -a main.pml && gcc -w -o pan pan.c && ./pan   # верификация
```

> **Важно про `spin -T`.** Флаг `-T` означает **«не делать отступы в выводе
> `printf`»** (проверяется через `spin --help`: `-T do not indent printf
> output`). Без `-T` SPIN печатает матрицу с большими отступами; с `-T` —
> ровно `[43,109,45]`. Это **не** «не выводить трассу».
>
> **Важно про `./pan` без `-N`.** В модели два never claim'а. `./pan` без
> `-N` берёт **первый по умолчанию — `liveness`** (SPIN прямо пишет
> `defaults to -N liveness`). То есть `make run` верифицирует **только
> `liveness`**. Чтобы проверить `safety`, нужно запустить вручную
> `./pan -a -N safety` (см. ниже).

### 11.1 Симуляция (`spin -T main.pml`)

Реальный вывод:

```
ltl liveness: <> ((done==1))
ltl safety: [] ((! (done)) || ((((((((((C[0]==43)) && ((C[1]==109))) && ...))))
Result Matrix C:
[43,109,45]
[31,16,11]
[73,51,31]
3 processes created
```

- Первые две строки — SPIN печатает формулы **после раскрытия макросов**:
  `done == true` стало `done==1`, а `done -> X` переписано в эквивалентное
  `!done || X` (импликация через дизъюнкцию). Это подтверждает, что формулы
  распознаны.
- `Result Matrix C: …` — вывод `printf` из `worker(0)`: матрица совпала с
  ручным эталоном из §10 → один прогон логически верен.
- `3 processes created` — это `init` + `worker(0)` + `worker(1)`.

Симуляция = **один** случайный путь. Она показывает, что модель *в принципе
работает*, но **не** доказывает свойство (доказывает верификация ниже).

### 11.2 Генерация верификатора (`spin -a main.pml`)

```
ltl liveness: <> ((done==1))
ltl safety: [] ((! (done)) || (...))
  the model contains 2 never claims: safety, liveness
  only one claim is used in a verification run
  choose which one with ./pan -a -N name (defaults to -N liveness)
```

На каждую `ltl{}` сгенерирован свой never claim; оба попали в `pan.c`; за
один прогон проверяется ровно один (поэтому `safety` гоняем отдельно).

### 11.3 Верификация `liveness` (`./pan -a -N liveness`)

```
pan: ltl formula liveness
(Spin Version 6.5.2 -- 18 September 2025)
        + Partial Order Reduction
Full statespace search for:
        never claim             + (liveness)
        assertion violations    + (if within scope of claim)
        acceptance   cycles     + (fairness disabled)
        invalid end states      - (disabled by never claim)
State-vector 292 byte, depth reached 455, errors: 0
     2301 states, stored (4602 visited)
     2923 states, matched
     7525 transitions (= visited+matched)
       14 atomic steps
unreached in proctype worker
        (0 of 93 states)
unreached in init
        (0 of 29 states)

```

| Поле | Смысл |
|---|---|
| `+ Partial Order Reduction` | редукция частичных порядков: SPIN отбрасывает эквивалентные перестановки независимых шагов воркеров. Результат не меняет, состояний резко меньше |
| `Full statespace search` | **исчерпывающий** перебор всех достижимых состояний |
| `acceptance cycles + (fairness disabled)` | для `liveness` ищутся циклы через допускающие состояния (вложенный DFS); без предположения справедливости |
| `invalid end states - (disabled by never claim)` | при активном claim проверка тупиков отключена — дедлок проверяется отдельно (§11.5) |
| `State-vector 292 byte` | размер снимка одного состояния (3 массива по 9 `int` + канал + PC трёх процессов) |
| `depth reached 455` | макс. длина пути DFS |
| `errors: 0` | **нарушений `liveness` не найдено** — главное число |
| `2301 stored (4602 visited)` | для liveness вложенный DFS: каждое состояние может посещаться дважды, поэтому `visited > stored` |
| `7525 transitions (= visited+matched)` | для liveness формула именно `visited+matched` (4602+2923) |
| `0 of 93 / 0 of 29` unreached | **весь** код `worker` и `init` достигнут — мёртвого кода нет |
| `claim liveness: 1 of 6 unreached, "-end-"` | финал-ловушка never claim **недостижим** ⇒ пути к нарушению нет ⇒ согласовано с `errors: 0` |

### 11.4 Верификация `safety` (`./pan -a -N safety`)

```
pan: ltl formula safety
State-vector 292 byte, depth reached 460, errors: 0
     2303 states, stored
      313 states, matched
     2616 transitions (= stored+matched)
        7 atomic steps
unreached in proctype worker
        (0 of 93 states)
unreached in init
        (0 of 29 states)
unreached in claim safety
        _spin_nvr.tmp:15, state 10, "-end-"
        (1 of 10 states)
```

Отличия от `liveness`:

- `safety` — инвариант, не нужен вложенный DFS: `transitions = stored +
  matched` (2303+313=2616), `matched` маленький (313), `errors: 0`;
- never claim `safety` сложнее (`10` состояний против `6` у `liveness`), но
  логика та же: `"-end-"` (state 10) недостижим → `1 of 10 unreached` →
  нарушения нет;
- ещё раз: эти числа получены **ручным** запуском `./pan -a -N safety`;
  `make run` сам по себе `safety` не проверяет (§11, врезка).

### 11.5 Итоговая сводка

| Свойство | Тип | формула | состояний claim | финал | errors |
|---|---|---|---|---|---|
| `liveness` | живость | `<> (done==1)` | 6 | 1 of 6 unreached | 0 |
| `safety` | безопасность | `[] (!done \|\| C верна)` | 10 | 1 of 10 unreached | 0 |

Везде `errors: 0`. Единственное «недостижимое» в `claim` — его терминал-
ловушка, и это **доказательство, что нарушения нет**, а не предупреждение.
Алгоритм через каналы корректен: программа завершается (`liveness`) и при
завершении `C = A×B` (`safety`).

## 12. Вариант коллег: `friends-main.pml` — общие переменные вместо каналов

Коллеги решают **ту же** задачу (параллельное умножение матриц), но обмен
делают **не каналами**, а **разделяемым массивом `C`** плюс счётчиком. Файл —
`part-1/docs/friends/friends-main.pml`. Их данные проще: матрица 2×2,
`A = [1,2; 3,4]`, `B = [5,6; 7,8]`, эталон `C = [19,22; 43,50]`.

### 12.1 Ключевые объявления (`friends-main.pml:1-10`)

```promela
#define N 2
#define P 2
#define N_SQ 4
byte A[N_SQ]; byte B[N_SQ]; byte C[N_SQ];
byte finished = 0;            // счётчик завершившихся воркеров
bool done_printing = false;   // их аналог нашего done
```

`byte` вместо `int` — потому что при `A,B = [1..8]` максимум элемента `C`
равен 50, что влезает в 0…255. У нас `int`, т.к. `test.py` подаёт
отрицательные значения (§13).

### 12.2 Воркер пишет прямо в общий `C` (`friends-main.pml:12-42`)

```promela
proctype worker(byte id) {
    byte i = id;
    ...
    do
    :: i < N ->
        ... свёртка ...
        idxC = i * N + j;
        C[idxC] = sum;        // 34: ПРЯМАЯ запись в общий массив C
        ...
        i = i + P;
    :: i >= N -> break;
    od;
    atomic { finished = finished + 1; }   // 42
    ...
}
```

Главное отличие от нас: здесь **оба** воркера пишут в `C` напрямую (строка
34). Гонки за **данные** при этом нет, потому что строки **не пересекаются**
(worker(0) → строка 0, worker(1) → строка 1) — каждый владеет своими
ячейками. Канал не нужен именно потому, что разбиение по строкам
непересекающееся.

### 12.3 Синхронизация: счётчик + охраняемая инструкция (`friends-main.pml:42-52`)

```promela
atomic { finished = finished + 1; }   // 42: атомарный инкремент счётчика

if
:: id == 0 ->
    finished == P;                    // 46: ЖДАТЬ, пока finished не дорастёт до P
    printf("Resulting Matrix C:\n");  // 47-49: печать
    printf("[%d, %d]\n", C[0], C[1]);
    printf("[%d, %d]\n", C[2], C[3]);
    done_printing = true;             // 50
:: else -> skip;
fi;
```

Два тонких момента:

1. **`atomic { finished = finished + 1; }`** (строка 42). Без `atomic`
   инкремент — это три шага (прочитать `finished`, +1, записать). Два воркера
   могут «разорвать» их и потерять одно приращение (классический race на
   счётчике). `atomic` делает инкремент неделимым. **У нас такой проблемы
   нет** — мы не считаем завершившихся воркеров, а полагаемся на блокирующее
   чтение из канала.
2. **`finished == P;`** (строка 46) — это **охраняемая инструкция** (§4.10):
   голое булево выражение как оператор. `worker(0)` **блокируется** на этой
   строке, пока `finished` не станет равно `P`, т.е. пока **оба** воркера не
   досчитают. Это их замена нашему «блокирующему `row_computed?`».

### 12.4 Сводка: каналы (наш) vs общие переменные (коллеги)

| Аспект | `main.pml` (наш, Вариант 1.4) | `friends-main.pml` (коллеги) |
|---|---|---|
| Размер матрицы | 3×3 | 2×2 |
| Тип элементов | `int` | `byte` |
| Связь процессов | канал `row_computed` (`!`/`?`) | разделяемый массив `C` |
| Кто пишет в `C` | **только** `worker(0)` | **оба** воркера (непересекающиеся строки) |
| Синхронизация | блокирующее чтение из канала | счётчик `finished` + охрана `finished == P` |
| Защита от гонки | архитектурная (один писатель) | `atomic { finished++ }` |
| Флаг для LTL | `done` | `done_printing` |
| `liveness` | `<> (done == true)` | `<> (done_printing == true)` |
| `safety` | `[] (done -> C[0]==43 && …)` | `[] (done_printing -> C[0]==19 && C[1]==22 && C[2]==43 && C[3]==50)` |
| Соответствие заданию | «обмен **каналами**» — буквально по ТЗ | обмен через общую память (другой подход) |

Главный вывод для понимания: оба решения корректны, но **наш** буквально
выполняет требование задания «обмен данными … с помощью каналов», тогда как
коллеги синхронизируются через разделяемую память и счётчик-семафор. Структура
LTL-свойств у обоих идентична — отличаются лишь имя флага и эталонные числа.

## 13. `test.py` — функциональное тестирование

`test.py` — **тестовый оракул** на Python: сравнивает вывод SPIN с
математически верным результатом. Алгоритм:

```
для N ∈ {2, 3, 4}:
    для каждого тест-кейса:
        1. C_эталон = A × B на чистом Python
        2. подставить A, B в копию main.pml (regex-замена)
        3. запустить spin (режим симуляции, без -a)
        4. распарсить "Result Matrix C:"
        5. сравнить → PASSED / FAILED
```

Виды кейсов: нулевые матрицы, матрицы единиц, 5 случайных (элементы −10…10 —
вот зачем `int`, а не `byte`). Реальный итог прогона:

```
=== ИТОГ: ВСЕ ТЕСТЫ ПРОЙДЕНЫ (21 тестов) ===
```

Важный нюанс: `test.py` использует **только симуляцию** (`spin main.pml`, без
`-a`). Он проверяет, что модель **считает правильный ответ** на конкретных
входах, но **не** проверяет LTL-свойства. Это тестирование функциональной
корректности, а не формальная верификация — они дополняют друг друга:
`test.py` проверяет много разных `A,B` на одном пути; `./pan` проверяет один
`A,B` на **всех** путях.

## 14. Как запускать

```bash
make run          # spin -T (симуляция) + spin -a + gcc + ./pan (только liveness)
./pan -a -N safety   # отдельно проверить safety (make run этого не делает)
make run-gui      # та же модель в графическом iSpin
make test         # python3 test.py — функциональные тесты (21 кейс)
```

`make run` (`part-1/Makefile:11-14`) выполняет:

1. `spin -T main.pml` — симуляция (один путь; `-T` = без отступов в `printf`);
2. `spin -a main.pml && gcc -w -o pan pan.c` — сгенерировать и собрать
   верификатор;
3. `./pan` — верификация; **без `-N` берётся `liveness` по умолчанию**.

Чтобы проверить **оба** LTL-свойства, после `make run` запусти вручную:

```bash
spin -a main.pml && gcc -w -o pan pan.c
./pan -a -N liveness    # errors: 0
./pan -a -N safety      # errors: 0
```

Ожидаемый результат по каждому свойству — `errors: 0`.
